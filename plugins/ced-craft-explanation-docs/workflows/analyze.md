# 解説の生成（analyze）

取り込み（`workflows/ingest.md`）のあと、`out/02`〜`out/11` を作る。Phase 1〜5・Step 1〜9。
プロンプトは `references/prompt-templates.md` の**該当するステップの節だけ**を読む。出力の書式は `references/output-formats.md` の「3-1. out/ の各ファイルの書式」。

## 前提

- 作業フォルダに `README.md`（`{{sections}}`・`{{overview}}`・`{{content_type}}` が埋まっている）と `01_source.md`（冒頭が埋まっている）がある。
- Step 0 の答え（内容の種類・目的・補足の扱い）が `out/00_run-report.md` にある。内容の種類は `references/content-types.md`。プロファイルは `references/profiles/<名前>.md`（取り込みで読んだもの）。
- 素材は `01_source.md` の本文。長いときは、セクションごとの範囲だけを読んでよい。

## 進め方の決まり

- **各ステップの終わりにユーザーへ確認しない**。ファイルを保存して次へ進む（質問は Step 0 の 1 回だけ）。
- `out/` のファイルの先頭には、メタ情報（`# 題`・`> 資料:`・`> ステップ:`・`> 生成日:`・`---`）を置く（`references/output-formats.md` の 3）。
- **本文に無いことを事実として書かない**。補足は `【補足】`、推測は `【推測】`。引用は本文から一字一句同じに切り出す（検査 C-8 が照合する）。
- 文字数は、書くときは上限より短めにする（要約 400・ポイントまとめ 70・活用案 400・システムプロンプト 2000）。実測は転記のあとの検査（C-6）が行う。**上限や数え方を変えて通さない**。
- すでに `out/` にあるファイルは、指示が無い限り作り直さない（部分実行・再実行のとき）。

## ステップごとの決まり

1. **Step 1**: 役割とユースケースの節を、内容の種類で決める。`## 3.` は README のセクション一覧どおりに `### <N>. <名前>（<範囲>）` を並べ、**すべてのセクション**に根拠の行を付ける（検査 C-7）。分割なしなら `### 1. 全体（分割なし）`。`## 5.` の質問は**ちょうど 5 問**。
2. **Step 2**: 回答の `###` は**ちょうど 5 つ**、質問と同じ順。`###` は質問の言い換えに留め、結論（数値・最大／最小・断定）は `- 回答：` に書く（見出しに詰めた断定が本文と食い違う誤りが、通し実行で出た）。
3. **Step 3**: **3 案の提案と選択をしない**。推奨の 1 案を採り、理由を `> 採用:` に書く。セクションが 4 つ以下ならセクション＝グループ。5 つ以上のときは、話題のまとまりで **3〜4 グループ程度**にまとめる（12 セクションでも 5 グループまで）。グループ名は重複させず、`out/05`・`out/08` で同じ名前を使う。採った案を `out/00_run-report.md` の「省いた確認」に書く。
4. **Step 4**: グループごとに 1 ファイル。`## テーマ：<グループ名>` と 6 つの `###`（名前・順序固定）。`### ポイントまとめ` は 70 字以内。
5. **Step 5**: `##` を使わない。最初の行は `### <総括タイトル>`。`- 横断分析：` の下に、視点ごとの子箇条書き（`  - <視点名>：<1 文>`）を **3〜4 個**書く。（1）（2）…を 1 行に並べて詰めない（検査 C-12）。最後に `- 一言まとめ：` の 1 行。
6. **Step 6**: 3 案、各案 400 字以内、字数は書かない。
7. **Step 7**: 「該当箇所」の引用は本文と一字一句同じ。**すべてのセクションが、どれかの「該当箇所」に出てくる**ようにする。
8. **Step 8-A**: 情報充足性の自己評価は必ず書く。足りなくても確認しない。`out/05`・`out/08` から補い、冒頭に補ったことを書く。
9. **Step 8-B**: 2000 字以内。コードブロックで囲まない。メタ情報に `> モデル: <実行したモデルの名前>`（実行したモデル 1 つだけ。自分が把握している名前をそのまま書き、ほかのモデルの名前を書かない）。内容の種類の到達点を Mission にする。
10. **Step 9**: 3 レベル×3 問。

## 部分実行・再実行

作業フォルダが既にあるとき（「Phase 4 だけ」「FAQ だけ作り直して」「続きから」）は、**先に状態を見る**。何も書かない。

```bash
<RUN> <SKILL_DIR>/scripts/scaffold.py <作業フォルダ>
```

標準出力の JSON の `steps`（Step ごとに `out/` のファイルがあるか）・`missing_steps`（足りない Step）・`groups`・`input_changed`（入力が作業フォルダを作った後に変わったか）を読む。

| 頼まれたこと | 動き |
|---|---|
| 続きから | `missing_steps` の Step だけを、表の順に作る。**あるファイルは作り直さない** |
| 「Phase N だけ」「<ステップ名>だけ」 | 指定された Phase・Step だけを作る。上の表の「読むもの」が `out/` に無ければ、足りない Step を伝えて止まる（`MISSING_OUT_FILE` の扱い。勝手に前の Step を作らない） |
| 「<ステップ名>を作り直して」 | そのファイルだけを作り直す（既存のファイルは、作り直す前に読んで、直す点だけを直す）。波及（下表）を伝える |
| 検査だけ・転記だけ | `workflows/review.md`・`workflows/assemble.md` |

- **指定していないファイルは書き換えない**（更新時刻も変えない）。作り直したら `assemble.py` をやり直す。内容が変わらないファイルは、スクリプトが書き直さない。
- `input_changed` が `true` のとき（入力の Markdown が、作業フォルダを作った後に書き換えられている）は、`01_source.md` が古い複製のままであることを伝える。**勝手に作り直さず**、「別名の作業フォルダで最初から作る」（`scaffold.py <入力> --dest <別の場所>`）を案内する。質問は増やさない（Q6 の答えが「続きから」だったときの注意として伝える）。
- `input_changed` が `null`（manifest が無い・入力のファイルが見つからない）のときは、止めずに続け、完了報告の「確認していないこと」に書く。

**作り直したときの波及**（作り直した Step を、後ろの Step がどう使うか。後ろの Step は、頼まれない限り作り直さず、「古くなっている可能性」として伝える）:

| 作り直す Step | 古くなる可能性があるもの |
|---|---|
| 1（`out/02`） | `out/03`（質問は `out/02` の §5）・`out/05`〜`out/11` |
| 3（`out/04`） | `out/05`・`out/08`（グループ名が一致しないと転記が `MISSING_OUT_FILE` で止まる）・`out/09` |
| 4（`out/05-N`） | `out/06`・`out/07`・`out/09` |
| 5・6（`out/06`・`out/07`） | `out/09` |
| 7（`out/08`） | `out/09`（補いに使った場合） |
| 8-A・8-B（`out/09`・`out/10`） | `out/10`・`out/11` |

## 終わったら

`out/00_run-report.md` の「省いた確認」（Step 3 で採った案と理由、Step 8-A で補った情報源）を書き足し、次の工程（転記）へ進む。
