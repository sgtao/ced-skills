# プロンプトテンプレート集

各ステップで使うプロンプトのテンプレート。`{変数名}` は、ファイルの内容やステップの成果物で置き換える。
**ステップごとに、該当する節だけを読む**（全部を一度に読まない）。出力の書式は `references/output-formats.md` の「3-1. out/ の各ファイルの書式」に従う。

## 共通の決まり（全ステップ）

- **素材は `01_source.md` の本文**（`<!-- source-body:start -->` より後ろ）。それ以外の知識は、補足として印を付けて使う。
- 根拠の示し方は、プロファイルの文書（`references/profiles/<名前>.md`）の「根拠の示し方」に従う。引用は本文から**一字一句同じ**に切り出す。途中を略すときは `…（中略）…`。
- 本文に無い例え・一般知識・筆者の整理は `【補足】`、推測は `【推測】`。本文に書かれていないことは「本文には書かれていない」と書く。
- 共通フレームワーク（AIM・MAP・Chain of Thought・Verifier・OCEAN・Refinement）を全ステップで統合的に使う。

| フレームワーク | 使い方 |
|---|---|
| AIM | Actor（役割）・Input（入力）・Mission（目標）を、各ステップの冒頭で明確にする |
| MAP | 前のステップの成果物を背景として参照する |
| Chain of Thought | 複雑な分析は、推論の過程を段階的に展開する |
| Verifier | 確認の質問・深掘りの質問で、理解の精度を確かめる |
| OCEAN | 具体性・論理性・主張・物語性・簡潔性を補強する |
| Refinement | 最後に、不整合・漏れ・代替解釈がないかを自己検証する |

- **各ステップの終わりに確認を取らない**。ファイルを保存して次へ進む。
- 資料・講義・動画・記事などの呼び方は、プロファイルに合わせる（`video` は「字幕」「動画」、`article` は「記事」、`document` は「資料」）。以下では「資料」と書く。

## Step 1 テンプレート：体系的解説（→ `out/02_overview.md`）

```markdown
# 資料：{title}
次の資料を深く理解したいです。次の条件・フレームワークに基づき、体系的に解説してください。

## Actor（役割）
あなたは「{content_types.md の役割}」として、論理性・正確性・教育効果を重視した説明を行ってください。

## Input（入力情報）
- 資料のメタ情報：下記「資料」
- 資料の本文全文（`01_source.md` の本文）
- 私の目的：{事前確認の答え。既定は「自分の学習・実務への応用」}

## Mission（到達目標）
AIを思考パートナーとして活用し、資料の構造理解・概念整理・ユースケース化・自己問いの深化を行う。

---

# 出力内容（見出しは次のとおり。output-formats.md の 3-1 に従う）

## 1. 要約
資料全体を、重要概念・因果関係・結論を中心に **400 字以内**でまとめる。

## 2. 例え話
先頭の行に `【補足】` と書く。抽象概念を、中学生でも直感的に分かる日常の例で説明する。

## 3. セクション別の解説
README のセクション一覧に沿って、`### <N>. <セクション名>（<範囲>）` ごとに、
- 何を教えているか（論理の流れ）を箇条書きで
- `- **根拠**：<プロファイルの形>「引用」` の行を 1 つ以上
セクションが「分割なし」のときは、`### 1. 全体（分割なし）` の 1 つにする。

## 4. ユースケース
{content_types.md の「ユースケースの節の中身」}。学習・ビジネスなら、いつ・どこで・だれが・なぜ・どうやって・目標を、各セクションまたは全体でまとめる。

## 5. 理解を深める質問
資料の内容を自分の文脈に統合できるようになるための**深掘りの質問を 5 つ**、番号つきリスト（`1.`〜`5.`）で。

## 6. 出力品質の検証
不整合や論理の飛躍はないか／重要点が漏れていないか／代替の解釈が必要な箇所はないか。

---

## 資料
- `title`: {title}
- `url`: {url（無ければこの行ごと省く）}

## セクション
{README のセクション一覧}

## 概要
{README の概要}

## 本文
{01_source.md の本文}
```

## Step 2 テンプレート：深掘りの質問への回答（→ `out/03_deep-questions.md`）

```markdown
あなたには、専門的な解説と論理的思考を行う「{content_types.md の役割}」の役割（Actor）をお願いします。以下の質問に回答する際、次のフレームワークを統合してください。
- AIM：役割の維持・入力の明確化・回答目標の明文化
- MAP：前のステップの成果物と本文を背景として活かす
- 思考促進：必要に応じて推論（Chain of Thought）、検証（Verifier）、改善提案（Refinement）を組み込む
- OCEAN：具体性・論理性・主張・物語性を補強
- 精度管理：論理の破綻・曖昧さ・事実誤認がないか軽い自己検証を実施

# 出力フォーマット（厳守）
- 5 つの質問のそれぞれについて、回答内容を短い要約にして **`###` の見出し**にする（**ちょうど 5 つ**。質問と同じ順）。
- 各見出しの下に、箇条書きで `- 回答：…`（Answer）と `- 解説：…`（Explanation：背景・理由・論理・重要ポイント）。**質問は書かない**（質問文は `02` にあり、転記で見出しになる）。必要に応じて具体例や短いストーリー。
- 本文に基づく部分には根拠を示し、本文に無い補足には `【補足】` を付ける。
- 自己検証の節は付けない。

### 質問
{out/02_overview.md の「5. 理解を深める質問」の 5 問}

### 回答
```

## Step 3 テンプレート：セクションのグルーピング（→ `out/04_grouping.md`）

**3 案の提案と選択はしない**。推奨の 1 案を採り、理由を記録する。セクションが 4 つ以下なら、セクション＝グループ（1 セクション 1 グループ）。分割なしなら、グループは 1 つ。

```markdown
次のセクションを、3 グループ程度に分類してください。条件：オリジナルのセクションの順序はそのまま。

### セクション
{README のセクション一覧}

## 指示
- 分類の軸（話題のまとまり・論理の流れ・読み手の使い方など）から、最もよいと考える **1 案**を決める。
- 出力（厳守）：1 行目に `> 採用: <分類軸の名称と、採った理由を 1〜2 文>`。続けて、グループごとに
  `## グループ<N>：<グループ名>`（N は 1 から連番。グループ名は重複させない）と、
  `- セクション<番号>：<名前>` の箇条書き。
```

## Step 4 テンプレート：グループ別の詳細解説（→ `out/05_group-analysis-<N>.md`、グループの数だけ）

```markdown
あなたは「{content_types.md の役割}」の役割（Actor）です。以下の指示に従い、本文の範囲内で深く考察した上で、簡潔かつ実用的な解説を作成してください。補助フレームワーク（AIM / MAP / Chain-of-Thought / Verifier / OCEAN / 精度管理）を適用してください。

## Mission（到達目標）
- 本文の情報だけを根拠として、テーマに関する深い解説を行う（追加情報の持ち込みは最小限）。
- 誰が読んでも構造が分かる、実務に落とせる「読みやすい要約＋箇条書き／表」で提示する。

## 制約（必ず守ること）
1. 解説は本文の範囲内の情報だけを主要根拠とする。外部の事実を使うときは `【補足】` と明記する。
2. 日本語で書く。
3. 最初に必ず `## テーマ：{グループ名}` を **h2** で書く（グループ名は `04_grouping.md` の名前と同じ）。
4. 本文は箇条書き・表を多用し、簡潔に。
5. `### ポイントまとめ` は **70 字以内**。
6. 最後の `### 確認の質問` は 1 つだけ（Verifier）。

## 出力構成（厳守。`###` の見出しもこの名前・この順）
- `## テーマ：{グループ名}`
- `### 背景`（1〜2 行。本文の根拠を短く示す）
- `### キー概念`（箇条書き。各行に根拠の場所を簡潔に）
- `### 詳細解説`（表または階層的な箇条書き。要点・因果関係・実務での適用方法）
- `### 注意点・限界`（本文の範囲での不確実性・推測の箇所。推測には `【推測】`）
- `### ポイントまとめ`（70 字以内）
- `### 確認の質問`（1 つ）

## Input（入力）
### このグループのセクションと本文：
{該当するセクションの本文（`01_source.md` から）}

### テーマ：
{グループ名と、含まれるセクションの一覧}
```

## Step 5 テンプレート：総括（→ `out/06_summary.md`）

```markdown
あなたは「{content_types.md の役割}」です。これまでの工程で作成した解説を統合し、初心者が「この資料の本質」を持ち帰れる総括を作成してください。

## Mission
- 個別のセクションの解説では見えなかった**横断的な気づき・構造・因果関係**を抽出する。
- 初心者が理解できる論理的で文脈豊かな総括にする。個別解説の繰り返しではなく、全体を俯瞰した上位概念を示す。

## 制約
1. 根拠は本文と、前の工程の解説に基づく。
2. 資料の外の比喩・補足を使うときは、先頭に `【補足】` を付ける。
3. 前の工程と同じ内容をそのまま繰り返さない（参照・引用はよい。コピーはしない）。

## 出力構成（厳守。`##` は使わない）
1. 本文の最初の行：`### <総括タイトル>`（この資料の本質を一言で表す）
2. `- 横断分析：…`（3〜4 つの視点で、個別解説を横断して見えるパターンや構造）
3. `- 一言まとめ：…`（一文）

## Input
### 前の工程の成果物：
{out/02〜05}

### 資料：
- `title`: {title}

### 概要：
{README の概要}
```

## Step 6 テンプレート：活用案（→ `out/07_reflection.md`）

globis 版の「振り返り文」を、**活用案**として最終ファイルに載せる。

```markdown
次の資料の内容に対して、活用案の文章を作成してください。

学んだ内容は、仕事や日常でどう活用できますか。具体的な場面を思い浮かべながら書いてください。

条件：
- 400 字以内の文章を 3 案。それぞれ異なる視点（例：実務の担当者の視点、学習者の視点、思考プロセスの視点）。
- 具体的な場面を思い浮かべた文章にする。本文に無い数字・事例を足すときは `【補足】`。
- **字数は書かない**（転記のときにスクリプトが実測で足す）。
- 出力（厳守）：`### 案1：<視点>`・`### 案2：<視点>`・`### 案3：<視点>`。各案は 1 つの段落。
```

## Step 7 テンプレート：FAQ（→ `out/08_faq.md`）

```markdown
あなたは**QA 作成の専門家**です。次の本文をもとに、初心者向けの FAQ を作成してください。
- 役割（Actor）：QA の専門家
- 入力（Input）：本文、前のステップの成果物
- 目標（Mission）：1 つの文章（または節）につき最低 1 つの質問と回答を作り、論理的で正確、理解しやすい FAQ にする

# 手順
1. 段階的に質問の意図を分析する（Chain of Thought）
2. 質問内容を 2 案つくり、最適なほうを選ぶ（Refinement）
3. 回答を本文に照らして確かめる（Verifier）
4. 各回答に、該当するセクション・具体例・論理的な説明を添える

# 出力形式（厳守）
グループごとに `## グループ<N>：<グループ名>`（`04_grouping.md` と同じ名前・順序）、その下に FAQ。

### <番号>. <題>
- **質問**：〜
- **回答**：〜
- **具体例**：〜（本文に無い例は `【補足】`）
- **該当箇所**：<プロファイルの形の根拠>「引用」

引用は**本文から一字一句同じ**に切り出す。段落をまたがない。すべてのセクションが、どこかの「該当箇所」に出てくるようにする。

## 本文
{該当グループのセクションの本文}
```

## Step 8-A テンプレート：システムプロンプト用の情報収集メモ（→ `out/09_input-memo.md`）

```markdown
あなたは資料の要約担当者です。次の情報源から、Step 8-B（システムプロンプト生成）に必要な「解説メモ」を作成してください。

## 入力の優先順位
1. README（題名・概要・要約）
2. out/06_summary.md（総括）

## 充足性の確認（Verifier）
上の 1・2 だけで、次の要件を満たす解説メモが作れるか自己評価する。
- 具体的な事実・数値・固有名詞が十分に含まれているか
- 内容の種類の判定に足る情報があるか

自己評価は**必ず行い、結果を書く**。**不足していると判断したとき**は、ユーザーに確認せず、`out/05_group-analysis-<N>.md` と `out/08_faq.md` から必要な部分を補い、**冒頭に補ったことを記録する**（どのファイルのどの節か）。

## 出力構成（厳守）
1. 情報充足性の自己評価（十分／不足＋理由。100 字程度）。補ったときはその旨
2. 解説メモ本文（事実・数値・固有名詞を保持した要約）

## Input
### README：{README の題名・概要・要約}
### 総括：{out/06_summary.md}
```

## Step 8-B テンプレート：システムプロンプト（→ `out/10_system-prompt.md`）

```markdown
あなたはプロンプトエンジニアリングのスペシャリストです。次の[解説メモ]に基づき、任意の LLM を「この資料の専門知識を持つガイド役」として振る舞わせる **2000 字以内**のシステムプロンプトを作成してください。

## 設計方針
1. 解説メモの知識を「Input Assets」としてプロンプトの中に埋め込む。
2. 埋め込む知識は、元の解説から具体的な事実・数値・固有名詞を保持する。
3. プロンプトの知識の範囲外の質問には「この範囲は私の専門外です」（または「資料では触れていません」）と答えさせる。
4. 本文に無いことは補足と断らせ、推測には「考察」と付けさせる。

## 内容の種類による到達点（Step 0 の判定。references/content-types.md）
{学習・ビジネス → 明日から使える行動／技術・ハウツー → 手順の再現と応用／考察・読み物 → 理解を深め、自分の意見を持つ}

## 含める要素
1. Role：利用者の理解度を見分けて、最適な深さで答えるガイド役
2. Input Assets：解説メモから抜き出した知識（具体的な事実を保持）
3. Mission：内容の種類に応じた目標
4. Output Style：具体例と論理的な根拠をセットで示す
5. Thinking Process：あいまいな質問には Verifier で確かめてから答える
6. Constraints：知識の範囲外への回答の制限、推測には「考察」と付ける

## 出力形式
コピーして使える Markdown のシステムプロンプト。コードブロックで囲まない。メタ情報に `> モデル: <実行したモデルの名前>` を足す（自分が把握している名前を 1 つ、そのまま）。

## [解説メモ]
{out/09_input-memo.md}
```

## Step 9 テンプレート：レベル別の質問例（→ `out/11_sample-questions.md`）

```markdown
生成したシステムプロンプトの強みを実感できる質問例を、「初心者向け」「中級者向け」「上級者向け」の 3 つで作成してください。

| レベル | 対象 | 質問の特徴 |
|---|---|---|
| 初心者向け | 基礎知識はあるが、触れて間もない | 基本概念の確認・日常との接続 |
| 中級者向け | 1 年程度の経験 | 実務での使い分け・判断の基準 |
| 上級者向け | 3 年以上の経験があり、さらに上を目指す | チームへの展開・メタ認知・応用 |

## 出力形式（厳守）
`### 初心者向け`・`### 中級者向け`・`### 上級者向け`（この順）。各見出しの下に、質問の箇条書き（3 問ずつ）。
```
